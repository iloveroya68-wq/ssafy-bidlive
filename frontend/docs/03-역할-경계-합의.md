```
  prediction/           FE1  예측 패널 (#action 슬롯)
  auth/ wallet/ room/ result/   FE1  (기존과 동일)
```

- 규칙 4 개정 문구(안): **FE2 소유 = `features/live/media·socket/`, `features/chat/`, `stores/live.ts`.**
  단 `features/live/LiveView.vue`·`LiveLayout.vue`는 FE1(프레임).
  상대 소유 컴포넌트는 **import는 자유, 내부 수정은 사전 합의**.
- 입찰·예측 패널을 `features/live/` 밖으로 빼는 이유: #action은 FE1 소유인데
  FE2 폴더 안에 두면 "폴더 = 소유권" 등식이 깨진다.

### 1-1. 경계 기준은 "소켓 수명주기 vs 표시" (2026-07-29 확정, S15P11A704-437)

폴더가 갈리지 않는 화면에서는 **폴더가 아니라 파일이** 경계다. 기준은 하나다 —
**소켓 수명주기(연결·구독·정리·이벤트 배선)를 지는 파일이 FE2**, 값을 받아 그리는 파일이 FE1.

`features/room/`(FE1 폴더) 안의 대기방이 그 예다.

| 파일 | 소유 | 근거 |
|---|---|---|
| `WaitingStage.vue` | FE1 | props 5개 + `emit('back')`. 스토어를 안 본다 |
| `WaitingLockedDock.vue` | FE1 | props + `stores/prediction` 상수. 소켓 없음 |
| `WaitingRoomView.vue` | **FE2** | `useLiveStore`, `connectWaitingRoom`/`disconnect`, 지연 `$reset` 방 스코프 가드 |
| `mocks/waitingRoom.ts` | **FE2** | 목 라이브 소스(§7과 같은 성격) |

라이브가 이미 같은 모양이다(프레임 FE1 / `media`·`socket` FE2) — 대기방만의 예외가 아니라 이미 쓰던
규칙의 적용이다. 그래서 §1의 "폴더 = 소유권"과도 부딪히지 않는다: `features/room/`은 FE1이고,
그 안에서 소켓 수명주기를 지는 파일 하나만 FE2다.

> **규칙 4의 "사전 합의"는 오너의 MR 승인으로 읽는다.** 상대 파일을 고치는 것 자체는 자유고,
> 그 MR에 오너를 리뷰어로 넣으면 그게 합의다. 티켓을 새로 파야 하는 것은 §3 시그니처나 화면 담당처럼
> **계약이 바뀔 때**뿐이다. (매 수정마다 선행 티켓을 요구하면 한 줄 고치는 데 왕복이 붙는다.)

## 3. `stores/live.ts` 계약 (커밋은 FE2)

> **2026-07-29 재작성 (S15P11A704-446).** 이전 판은 「입찰 결과가 소켓(`BID_RESULT`)으로 온다」는 전제로
> `bidStatus`·`bidRejectReason`·`placeBid`를 계약에 뒀다. 명세에 `BID_RESULT`가 없고 BID-06이 REST 201로
> 개인 결과를 동기 반환하므로 그 전제가 성립하지 않는다(§6-9). 아래가 **현재 코드와 일치하는 계약**이다.

FE1 화면(입찰·예측 패널, 타이머 칩)이 의존하는 시그니처. 이름·타입이 합의 대상이다.

### 3-1. 입찰 값은 두 갈래다

| 갈래 | 값 | 갱신 주체 |
|---|---|---|
| **집계** (비크리 공개 허용 범위) | `bidCount`·`participantCount` (`number \| null`) | 소켓 `BID_ACCEPTED` · WS-03 스냅샷 |
| **내 것** | `myBid` (`number \| null`) · `myParticipationType` (`'NONE' \| 'BID' \| 'PREDICTION'`) | **BID-06 REST 응답** — FE1이 `$patch` |
| **내 예측** | `myPredictedPrice` (`number \| null`) · `myStakeAmount` (`number \| null`) | **WS-03 스냅샷 전용** — 재접속 복원용이고 제출 시 `$patch`하지 않는다 |
| **예측 정산 신호** | `predictionSettlement` (`PredictionSettledData \| null`) | 소켓 `PREDICTION_SETTLED` (PRED-03) — 화면이 watch해 PRED-02 재조회 (S15P11A704-543) |

`null`은 "아직 모름"이고 `0`("아무도 없음")과 구분한다 — 스냅샷 도착 전 0을 그리면 없는 사실을 단정한다.

**`bidStatus`·`bidRejectReason`은 계약에 없다.** 스토어에 한 번도 존재한 적 없고(소스 grep 0건),
개인 결과 채널로 쓸 수도 없다 — `BID_ACCEPTED`의 `data`는 `bidCount`·`participantCount`·`vibeMessage`
셋뿐이라(규칙 6: 금액·입찰자·순위 비공개) **누구의 입찰이 접수됐는지 식별할 수단이 없다.**

### 3-2. 입찰 제출은 스토어를 거치지 않는다

```ts
// FE1 패널이 직접 await — shared/api/bids.ts (Idempotency-Key 헤더)
const result = await placeBid(auctionId, { amount }, idempotencyKey, { previousBidAmount, availableBalance })
// 성공 → FE1이 스토어에 반영
live.$patch({ myBid: result.myBidAmount, myParticipationType: 'BID' })
```

거절도 HTTP 에러로 온다(`BID_BELOW_RESERVE_PRICE`·`BID_NOT_HIGHER_THAN_PREVIOUS`·
`INSUFFICIENT_AVAILABLE_BALANCE`·`PREDICTION_ALREADY_JOINED` 등) — 패널이 `bidErrorMessage(error)`로 그린다.
예측 제출(PRED-01)도 같은 모양이다.

### 3-3. 스토어 액션은 소켓 수명주기와 채팅뿐

```ts
connect(roomId: number, opts?: { questions?: boolean }): Promise<void>
                                                  // 입장 — 모드 인식 단일 진입점(실 STOMP / 목 피드)
                                                  // opts.questions는 판매자 화면(콘솔)만 켠다(541)
connectWaitingRoom(roomId: number): Promise<void> // 대기방 — 라이브와 같은 토픽(ROOM-07)
disconnect(): Promise<void>                       // 퇴장 — 구독·타이머·전송함수 정리
joinRoom(roomId: number): void                    // 방 스코프 초기화($reset + roomId + roomSession)
sendChat(text: string, isQuestion?: boolean): void        // CHAT-01·06
markChatFailed / retryChat / dismissChatFailed(id): void  // 전송 실패 조치
loadOlderChat(): Promise<void>                    // 과거 조회(REST)
```

입찰·예측 제출 액션은 여기 없다 — 3-2가 이유다. 이 목록은 **소켓으로 오는 것과 소켓으로 보내는 것**만 담는다.

### 3-4. 화면의 언마운트 정리는 `roomSession`으로 판정한다 (2026-07-29, S15P11A704-367)

세 화면(Live·Waiting·Console)은 떠날 때 `disconnect()` 뒤에 `$reset()`을 건다. 그 `$reset()`이
**다음 화면이 이미 입장한 뒤에 도착**하면 방금 세운 상태를 지우므로, 화면은 자기 입장을 캡처해 두고
아직 살아 있을 때만 지운다.

```ts
const leaving = live.roomSession
void live.disconnect().then(() => {
  if (leaving !== live.roomSession) return   // 다음 화면이 입장했다 — 건드리지 않는다
  live.$reset()
})
```

`roomSession`은 `joinRoom()`이 들어올 때마다 새로 발급하는 **입장 일련번호**다(state, `$reset` 시 0).

⚠️ **`roomId`로 대조하면 안 된다.** 같은 방을 다시 여는 경로에서 번호가 같아 통과한다 —
콘솔의 「라이브로 이동」이 실제로 그 경로다. 방이 아니라 **입장**이 판정 기준이다.
(같은 이유로 `329`도 `disconnect(roomId)` 대조안을 물리치고 세대 카운터를 골랐다.)

  마감 시각은 목록 응답의 `endAt`(S15P11A704-523), 오프셋은 목록·상세의 `serverTime`(S15P11A704-265).
  **둘 중 하나만 채워도 `--:--`다** — `useCountdown`이 마감 시각 없이는 오프셋을 보지도 않는다.

## 4-1. 참여 역할 — 입찰과 예측은 배타적이다 (BID·PRED)

한 방에서 한 사람은 **입찰자(BIDDER) 또는 예측자(PREDICTOR) 중 하나로만** 참여한다.
DB 근거: `auction_participant`의 `UNIQUE (auction_room_id, member_id)` +
`CHECK (participation_type IN ('BIDDER','PREDICTOR'))`. `bid`·`prediction` 모두 이 참여 행을 FK로 참조한다.

**강제 선택은 없다.** 입장 시 역할을 고르게 하지 않는다 — 아무것도 하지 않고 구경만 해도 된다.
참여 행은 **첫 입찰 또는 첫 예측 시점에 생성**된다(BE 확인 완료). 따라서 상태는 둘뿐이다.

| 상태 | 참여 행 | 화면 |
|---|---|---|
| 참여 전 (구경) | 없음 | 입찰·예측 패널 **둘 다 사용 가능** |
| 참여 후 | 있음 (타입 확정) | 선택한 쪽만 사용 가능, 다른 쪽 **잠김** |

- **확정 이후 역할 변경은 불가하다** (기획·BE 확정). 변경 API는 제공되지 않는다.
  `bid`·`prediction`의 FK가 `ON DELETE RESTRICT`인 것과도 일치한다.
  따라서 FE는 역할 변경 UI를 만들지 않고, 되돌리기 흐름도 상정하지 않는다.
- **첫 액션에는 확인 단계를 둔다.** 되돌릴 수 없는 선택인데 버튼만 봐서는 알 수 없기 때문이다.
  예: "입찰에 참여하면 이 방에서는 예측 베팅에 참여할 수 없습니다. 계속하시겠어요?"
  두 번째 입찰부터는 띄우지 않는다(입찰은 `sequence_no`로 여러 번 가능).
  예측은 `prediction.auction_participant_id`가 UNIQUE라 애초에 1회뿐이다.
- **잠긴 쪽은 숨기지 않고 안내를 남긴다.** 패널이 통째로 사라지면 레이아웃이 흔들리고
  사용자가 기능이 없어진 것으로 오해한다. "입찰자로 참여 중입니다" 수준의 안내로 자리를 유지한다.

**모드 전환 UI 자체는 있다 (와이어프레임 대조, 2026-07-22).** `live` 화면의 레일 상단에
`상향 입찰` / `예측 베팅` 전환 버튼이 실재하고, 반대편 독은 사라지는 대신 잠금 문구로 덮인다:
"🔒 이 방에 이미 입찰했어요. 입찰과 예측 베팅은 한쪽만 참여할 수 있어요 (상호 배타 — 2등가 조작 방지)".
즉 **보는 것은 자유롭게 오갈 수 있고, 잠기는 것은 참여(제출)뿐**이다.
"토글을 만들지 않는다"가 아니라 "토글이 역할 변경 요청이 되지 않는다"로 읽어야 한다.

```ts
roomId: number                    // 필수 (= auctionId)
highlightQuestions?: boolean      // CHAT-06 질문 강조 (라이브에서만 켤 수도)
disabled?: boolean                // 입력 잠금 (종료 후 등)
title?: string                    // 헤더 라벨 (기본 '실시간 채팅', 대기방은 '대기 채팅')
hint?: string                     // 정적 안내 스트립 (서버 고정 공지와 별개인 문맥 안내)
disabledText?: string             // disabled일 때 잠금 문구 — 사유는 컨테이너가 안다 (기본: 종료 후)
canPin?: boolean                  // CHAT-02 고정 공지 등록·해제 액션 노출 (판매자만, 기본 false)
canDelete?: boolean               // CHAT-01 메시지 삭제 액션 노출 (판매자·운영자, 기본 false)
```

`canPin`과 `canDelete`는 판정이 다르다 — 고정은 판매자 전용(서버 403 `NOT_AUCTION_HOST`)이고,
삭제는 판매자와 `ADMIN` 둘 다 허용이다(서버 403 `CHAT_DELETE_FORBIDDEN`). 한 값으로 합치지 않는다.

props가 늘어나는 건 FE2 자유. **기존 prop의 이름·타입 변경만 사전 공유.**

## 6. 소켓 이벤트 계약 (백엔드 명세 기준, 2026-07-23 재작성)

> **출처: 백엔드 「최종(종합) 명세서」의 API 명세 테이블·WebSocket 이벤트 명세.**
> 기존 §6은 대조 전 초안이라 이벤트 이름이 대부분 실제와 달랐다 — 마이그레이션은 §6-7 참조.
> 이름·`data` 필드는 **백엔드 명세가 단일 소스**이며 이 표는 그 사본이다. 임의로 추가·개명하지 않는다.

모든 이벤트는 `{ type: string, data: object }` 래핑 (백엔드 공통 규격, AGENTS.md 규칙 9).

- `destination`은 메시지 본문에 넣지 않는다.
- `auctionId`는 구독 destination에 이미 있으므로 본문에서 제외한다.
- `serverTime`은 공통 필드가 아니라 `TIME_SYNC`의 `data`에만 들어간다.
- `eventId`·`sequence`는 초기 구현에서 쓰지 않는다(중복·유실 복구가 필요해지면 추가).

### 6-1. 연결·인증 (WS-01)

```
CONNECT /ws
accept-version:1.1,1.2
Authorization:Bearer {accessToken}
heart-beat:10000,10000
```

- 서버가 토큰을 검증해 세션 `Principal(memberId)`을 확정한다. **SEND·SUBSCRIBE의 회원 식별은 항상 세션 Principal 기준**이라 클라이언트가 memberId를 실어 보내지 않는다.
- 토큰 만료 시 **수신은 grace 기간 동안 유지되고 발신만 `AUTH_EXPIRED`로 차단**된다 → `/app/auth/renew`로 재인증.
- 실패 코드: `AUTH_INVALID`(서명·회원 상태), `AUTH_EXPIRED`(연결 시점 만료).

| destination | 용도 | 기능 ID |
|---|---|---|

### 6-5. 재접속·스냅샷 (WS-03)

재접속 시 이벤트 누락·역전을 막기 위해 **서버 권위 스냅샷 + 단조 증가 `stateVersion`**을 쓴다.

```
GET /api/v1/auctions/{auctionId}/realtime-state
→ { stateVersion, auctionStatus, endAt, remainingSeconds, extendCount,
    bidCount, bidParticipantCount, viewerCount,
    myBidAmount, myParticipationType, pinnedNotice, amIMuted }
```

절차:

1. SUBSCRIBE에 `receipt`를 넣고, RECEIPT 수신 전 이벤트는 **버퍼링**한다.
2. 스냅샷을 조회한다.
3. 버퍼에서 `event.stateVersion <= snapshot.stateVersion`인 것은 폐기한다.
4. 더 큰 버전만 오름차순 적용하고, 이후 실시간 이벤트를 처리한다.
5. 버전이 불연속·역전이면 **추측 적용하지 말고 스냅샷을 다시 조회**한다.

- `myBidAmount`는 본인 값만, 미입찰이면 `null`.
- `myParticipationType`은 `NONE | BID | PREDICTION` — **§4-1 배타 잠금 상태를 재접속 후 복원하는 근거값**이다.
- `bidParticipantCount`는 고유 회원 수(상향 입찰 중복 제거).

### 6-6. 목 드라이버가 지켜야 할 것

§7의 목 드라이버도 **위 이벤트 이름·필드를 그대로** 쓴다. 실소켓 전환 시 핸들러를 그대로 재사용하는 것이 §7의 전제이므로, 목에서만 통하는 이름을 만들면 그 전제가 깨진다.

이 절에 있던 항목(BID-10 집계 중 이벤트 타입명 부재, `PREDICTION_SETTLED`의 폐기 설계 잔재
`winningBucket`·`totalPool`, 상태 변경 이벤트의 `stateVersion` 포함 여부)은 **S15P11A704-221**로 옮겼다.
이후 구현에서 나온 것(예측 결과 조회 API 부재, 유찰 사유 코드 `FORCED`/`FORCED_END` 불일치,
`AUCTION_STARTED`의 최상위 필드)은 **S15P11A704-227·266**에 있다.

`PREDICTION_SETTLED`는 확정 명세에서 `settlementStatus`·`settledCount`로 재정의됐다(구간 설계 어휘 제거,
S15P11A704-541). FE는 이 이벤트를 **정산 종료 신호로만** 쓴다 — 분포·배당은 이벤트가 아니라
`GET /auctions/{id}/prediction-results`(PRED-02)로만 가져온다.
**2026-08-01(543) 갱신:** 「스토어 상태를 바꾸지 않는다」는 더 이상 사실이 아니다. 명세 처리 규칙이
"수신하면 PRED-02를 호출한다"이므로 핸들러가 수신 사실을 `live.predictionSettlement`(§3-1)에 담고,
예측 결과를 그리는 화면이 그걸 watch해 **1회 재조회**한다(폴링·타이머 없음).
바뀐 것은 신호를 담는 필드 하나뿐이고, 이벤트가 분포·배당을 싣지 않는다는 원칙은 그대로다.

> ⚠️ 실서버 payload는 아직 `data: {}`다(`PredictionSettledMessage.completed()` — 명세의 두 필드를
> 채우지 않는다). 그래서 FE는 `settlementStatus` 값으로 분기하지 않고 "수신했다"만 쓴다.
> 재조회가 다시 409면 기존 안내 문구로 떨어진다.
>
> **2026-08-01(546) 갱신:** 결과 화면(`ResultView`)이 마운트에서 `live.connect(auctionId)`로 **직접
> 메인 토픽에 붙는다** — 라이브가 언마운트하며 자기 연결을 끊으므로, 그 전에는 이 watch에 도달하는
> 신호가 「라이브에 머무는 동안 온 것뿐」이었다(즉 실전에서 발화하지 않았다). 이제 결과 화면을 열어 둔
> 채 정산이 끝나면 그 신호로 밴드가 자동으로 채워진다. 결과 전용 경량 연결 옵션을 만들지 않고
> `connect`를 재사용한다 — 딸려 오는 채팅 구독은 **수신만 하고 결과 화면이 읽지 않아** 무해하고,
> WS-03 스냅샷 404는 라이브가 이미 매번 삼키는 것이다. 정리는 언마운트의 `live.disconnect()`이고,
> 다음 화면이 먼저 연결을 세운 경우는 스토어의 연결 세대 가드(S15P11A704-329)가 막는다.
> **목 모드는 붙지 않는다** — 목 피드는 `PREDICTION_SETTLED`를 보내지 않고 결과 화면이 안 읽는
> 집계만 흔든다. 안내 문구 자리의 「다시 확인」 버튼(`PredictionBandChart`의 `retry`)은 그대로 남아
> 목 모드·연결 실패·신호 유실의 수동 계기를 맡는다.
>
> ⚠️ **알려진 부작용 — 결과 화면 체류자가 종료된 방의 시청자로 집계된다.** BE
> `ViewerSessionStompEventListener`는 경매 상태를 보지 않고 `auctionId`로 해석되는 SUBSCRIBE를 전부
> 시청 세션으로 기록하고 `VIEWER_COUNT`를 다시 쏜다(`ViewerSessionTrackingService.subscribe` →
> `viewerCountService.refresh`). 결과 화면은 `viewerCount`를 그리지 않아 **렌더에는 영향이 없지만**,
> 집계 기준이 메인 토픽 구독 자체라 「메인 토픽만 구독하는 경량 옵션」으로도 피할 수 없다 —
> 게이트를 걸 자리는 BE다. 시청자 수의 의미를 「라이브 중 시청자」로 좁히려면 BE 이슈로 다룬다.

### 6-9. §3 계약 개정 경위 (종료 — 2026-07-29)

§3은 `bidStatus`/`bidRejectReason`을 두고 **"입찰 결과는 소켓(`BID_RESULT`)으로 흐른다"**는 전제 위에 설계됐다.
그런데 명세상 **`BID_RESULT` 이벤트는 없고, BID-06이 REST 201로 개인 결과를 동기 반환**한다:

```json
{ "myBidAmount": 82000, "previousBidAmount": 70000, "additionalHoldAmount": 12000,
  "totalHeldAmount": 82000, "availableBalance": 118000, "submittedAt": "..." }
```

거절도 HTTP 에러로 온다(`BID_BELOW_RESERVE_PRICE`, `BID_NOT_HIGHER_THAN_PREVIOUS`, `INSUFFICIENT_AVAILABLE_BALANCE`, `PREDICTION_ALREADY_JOINED` 등).
따라서 "`placeBid`가 Promise를 반환하지 않는다"는 §3의 근거가 성립하지 않는다.

**결론 (2026-07-29):** `bidStatus`·`bidRejectReason`을 계약에서 뺐고, `placeBid`도 스토어 액션이 아니다.
개정된 계약은 §3이다. 224(계약 개정)·299(화면이 스토어 서버 권위 값을 읽도록 전환) 모두 종료됐다 —
`LiveView`가 `live.bidCount`·`live.participantCount`를 직접 읽고, 개인 결과는 REST 응답으로 `$patch`한다.
로컬 `ref`와 스토어가 공존하던 상태는 해소됐다.

> ⚠️ 이 절은 2026-07-29까지 「224에서 다룬다」·「두 집계값을 화면이 읽으면 항상 0」으로 남아 있었다.
> 224는 그전에 완료됐고 299도 종료돼 두 문장 모두 사실이 아니었다 — 문서만 읽고 로컬 `ref`를 새로
> 만들면 방금 없앤 이중 소스가 되살아나는 자리였다. 완료된 티켓을 미해결로 적어 두지 않는다

## 7. 목(mock) 범위 — "목 소켓"이 아니라 핸들러 드라이버

- 가짜 STOMP 클라이언트(토픽 구독·연결 상태 흉내)는 **만들지 않는다.**
- FE2가 만드는 것: ① 이벤트 핸들러(`{type,data}` → 스토어 갱신, **실소켓에서 그대로 재사용**),
  ② 그걸 두드리는 `setInterval` 드라이버(`src/mocks/liveFeed.ts`, ~50줄),
  ③ 스토어 fixture·가짜 action.
- FE1 화면 개발에는 fixture + 가짜 action이면 충분 — 목 피드는 데모(중간 발표)용.
