# 운영자 콘솔 — 신고 목록과 강제 종료

`S15P11A704-525`. DEAL-09 강제 종료(`522`)가 붙었지만 **누를 화면도, 누를 수 있는 계정도 없다.**
이 문서는 그 둘을 채우는 설계다.

## 배경

착수 전 `dev`에서 확인한 것들이다. 설계가 여기 얹혀 있으니 바뀌었으면 설계부터 다시 본다.

- **강제 종료 API는 있다** — `POST /api/v1/admin/auctions/{auctionId}/force-end`, `hasRole("ADMIN")`.
  - ⚠️ **2026-07-31 정정(S15P11A704-537).** 이 설계는 「강제 종료하면 방이 `ENDED`가 되므로
    입찰·예측·채팅 입력도 함께 막힌다」를 전제로 썼는데 **사실이 아니었다.** 입찰·예측 접수는
    Postgres가 아니라 Redis 상태 Hash의 `status`만 보고, 강제 종료가 그 Hash를 안 닫아 원래
    마감까지 입찰이 계속 접수됐다(그 홀드는 아무도 안 풀어 잔액이 묶였다). 537에서
    `RedisAuctionStateCloser`가 `AUCTION_CANCELED`를 받아 닫도록 고쳤다. **채팅 차단은 여전히
    미이행이다** — 채팅 전송 핸들러(CHAT-01) 자체가 아직 없다. 화면 문구에 「채팅도 막힌다」를
    쓰지 않는다.
- **신고 접수도 있다** — `AuctionReportController` (DEAL-04). 사유 4종:
  `FALSE_LISTING` · `PROHIBITED_ITEM` · `INAPPROPRIATE_BROADCAST` · `OTHER`.
- **신고 조회는 없다.** `docs/api/report/`에 계약이 POST 하나뿐이다. 명세부터 새로 쓴다.
- **`report` 테이블은 운영 처리를 전제하고 설계돼 있다** — `status`·`processed_by_member_id`·
  `resolution_note`·`processed_at`에 `idx_report_status_created`까지 있다. 지금은 아무도 안 쓴다.
- **프론트에 admin 라우트가 하나도 없다.** 화면 하나가 아니라 틀부터 새로 만든다.
- **`ADMIN` 계정이 0개다.** 아래 「ADMIN 승격」 참조.

## 범위

**들어가는 것**

1. 신고 조회 API (`GET /api/v1/admin/reports`) — 경매별 집계
2. `ADMIN` 승격 초기화 (환경변수 기반)
3. `/admin` 화면 — 신고 탭 + 방 탭, 행마다 강제 종료

**빼는 것과 이유**

- **신고 처리(`PATCH`)** — `report.status`를 바꾸는 쓰기 API. 강제 종료하면 방이 `ENDED`가 되어
  목록에서 내려가므로, 「처리한 신고가 쌓인다」 문제가 쓰기 없이 풀린다. 상태 전이 규칙을 정하는
  비용이 지금 얻는 것보다 크다.
- **개별 신고 펼치기** — 신고 1건씩의 사유·설명을 보는 상세. 집계(`금지 품목 5 · 허위 3`)만으로
  「이 방을 끝낼까」 판단이 선다. 상세 API가 하나 더 필요해진다.
- **회원 관리·제재** — 이 화면의 목적은 강제 종료 하나다.
- **라우터 ADMIN 가드** — 아래 「비ADMIN 진입」 참조.

## 1. 신고 조회 API

```
GET /api/v1/admin/reports?includeEnded=false&cursor=&size=20
```

**경매별로 묶어서** 돌려준다. 운영자가 판단하는 단위가 신고 1건이 아니라 방이기 때문이다.

```jsonc
{
  "items": [{
    "auctionId": 9203,
    "title": "빈티지 카메라",
    "thumbnailUrl": "https://...",
    "sellerNickname": "서연***",
    "status": "LIVE",
    "reportCount": 8,
    "reasonCounts": [
      { "reasonCode": "PROHIBITED_ITEM", "count": 5 },
      { "reasonCode": "FALSE_LISTING",   "count": 3 }
    ],
    "latestReportedAt": "2026-07-31T10:31:00+09:00"
  }],
  "nextCursor": null,
  "hasNext": false
}
```

- 기본은 방 상태가 `WAITING`·`LIVE`인 것만. `includeEnded=true`면 `ENDED`까지 포함
- 정렬 `latestReportedAt DESC`, 커서 페이징은 기존 패턴(`AuctionRoomListCursor` 등)을 따른다
- `reasonCounts`는 많은 순. 동수면 `reasonCode` 사전순으로 고정한다 — 순서가 흔들리면 화면의
  「금지 품목 5 · 허위 3」이 새로고침마다 뒤바뀐다
- `report.status`는 **읽지도 쓰지도 않는다.** 전부 `RECEIVED`라 필터로서 의미가 없다
- 권한은 `SecurityConfig` 경로 매처 `hasRole("ADMIN")` + CSRF 예외 목록 등록.
  `522`와 같은 방식이다 — 이 레포는 `@EnableMethodSecurity`를 켜지 않는다
- 조회 API 관례대로 JPA 엔티티 없이 `EntityManager.createNativeQuery` + 도메인 record

**명세 문서**를 `backend/docs/api/report/`에 새로 만든다. Notion 원본에 없는 계약이므로
「로컬에서 신설」임을 문서 머리에 명시한다.

## 2. ADMIN 승격

**시드로 계정을 만드는 건 불가능하다.** 로그인 경로가 카카오 OAuth뿐이고
`social_account`에 실제 `provider_user_id`가 붙어야 들어올 수 있다. 비밀번호 개념이 없다.
따라서 「계정 생성」이 아니라 **「가입한 회원의 승격」**만 가능하다.

**환경변수 기반 초기화**를 쓴다.

```
ADMIN_MEMBER_IDS=42,57
```

부팅 시 `ApplicationRunner` 하나가 `UPDATE member SET role='ADMIN' WHERE member_id IN (:ids)`를
실행한다. 값이 비면 아무것도 하지 않는다. 멱등이다.

**Flyway 마이그레이션에 `UPDATE ... WHERE member_id=N`을 넣지 않는다.** 두 가지가 걸린다 —
특정 개인의 id가 git 히스토리에 영구히 남고, **로컬 DB의 `member_id`는 사람마다 달라서 다른 사람
환경에서 엉뚱한 회원이 ADMIN이 된다.**

**알려진 한계:** 이 방식은 env 파일이 곧 권한이다. 지금 규모에서는 받아들이고, 회원 관리 화면이
생기면 그쪽으로 옮긴다.

절차(카카오 로그인 → 본인 `member_id` 확인 → env 등록 → 재기동)는 명세 「구현 메모」에 적는다.

## 3. `/admin` 화면

`AdminView.vue` 하나. 탭 2개.

| 탭 | 출처 | 쓰임 |
| --- | --- | --- |
| 신고 접수 방 | `GET /admin/reports` | 기본 진입점 |
| 전체 방 | 기존 `getAuctionRooms({ status })` | 신고가 없는 방을 끝내야 할 때 |

각 행에 **2단계 인라인 강제 종료**를 둔다.

```
1단계
│ 빈티지 카메라   LIVE   신고 7          │
│ 금지 품목 5 · 허위 3         [강제 종료] │

2단계
│ 빈티지 카메라   LIVE   신고 7          │
│ 입찰·예측 전액 환급됩니다              │
│ 사유: 금지 품목    [한 번 더 눌러 종료] │
```

- 로직은 `useAdminForceEnd`로 뽑는다. **타임아웃 자동 해제**와 **다른 행을 건드리면 풀림**은
  `useDealAction`(수령 확인)·`useRoomDelete`의 규칙과 값을 그대로 맞춘다
- 전송하는 `reason`은 **운영 고정값 `ADMIN_FORCE_END`** 하나다. 운영자가 고르지 않는다.
  화면의 「사유: 금지 품목」은 `ReportedAuctionRow`가 자기 `reasonCounts`로 계산하는
  **표시 전용**이고 요청에는 실리지 않는다.
  DEAL-09 명세 예시는 `POLICY_VIOLATION`이지만 **값 목록을 정해 둔 곳이 없고 서버도 비어 있지만
  않으면 받는다.** 나중에 값 목록이 확정되면 그때 맞춘다
  - ⚠️ **2026-07-31 정정 (MR !260 리뷰).** 원안은 「그 방의 최빈 신고 사유 코드로 자동 채운다」였다.
    뒤집은 근거는 **브로드캐스트 경로**다: `AuctionForceEndService`가 그 `reason`을 그대로
    `AuctionCanceledEvent`에 실어 `/topic/auctions/{auctionId}`로 발행하고
    (`StompAuctionCanceledEventPublisher`), 그 토픽은 **그 방에 있던 시청자 전원이 구독한다**
    (`liveSocket.ts`). `PROHIBITED_ITEM`·`FALSE_LISTING`은 **판매자에 대한 혐의**라
    시청자 브라우저에 도착할 값이 아니다 — 지금 `handlers.ts`가 `_data`를 안 읽어 화면에
    안 뜰 뿐이고, 페이로드에는 들어간다. AGENTS.md 절대 규칙 6(시청자에게 새는 값을 만들지 않는다)과
    같은 기준이다
- 종료에 성공하면 그 행을 목록에서 제거한다. 전체를 다시 부르지 않는다
- 새 색을 만들지 않는다. `bg-terra`(강제 종료)·`bg-faint`·`bg-surface`만 쓴다.
  탭 틀은 `MyPageView`가 가장 가깝다

**`reason`의 성격을 알고 쓴다.** 지금 `reason`은 DB에 남지 않으므로 **감사 기록이 아니다.**
동시에 `AUCTION_CANCELED`로 방 전체에 나가므로 **비공개 값을 담는 자리도 아니다.**
저장은 안 되고 유출은 되는, 공개 라벨 하나로만 쓴다.

**비ADMIN 진입**은 라우터 가드를 만들지 않는다. 서버가 403을 주므로 화면에서 「권한이 없어요」를
그린다. 가드를 두면 role 판정이 서버와 라우터 두 곳에 생기고, 둘이 어긋나면 조용히 갈린다.

## 오류 처리

| 상황 | 화면 |
| --- | --- |
| 목록 403 | 「권한이 없어요」 — 비ADMIN 진입의 정상 경로다 |
| 목록 실패 | 「불러오지 못했어요」 + 다시 시도 |
| 종료 409 (`AUCTION_NOT_ENDABLE`) | 「이미 종료됐거나 삭제된 경매예요」 + 그 행 제거 — BE가 `deleted() \|\| !endable(status)`를 한 코드로 묶어(운영자용이라 존재를 숨길 이유가 없어 404 대신 409, MR !246) 두 경우가 다 온다 |
| 종료 404 | 「경매를 찾을 수 없어요」 + 행 제거 |
| 종료 그 외 | 「종료하지 못했어요」, 행은 유지하고 2단계만 푼다 |

## 테스트

- **BE** — 어댑터 집계(경매별 묶음·`reasonCounts` 정렬 고정), `includeEnded` 분기,
  권한 통합 테스트(ADMIN 200 / USER 403 / 비로그인 401), 승격 초기화 멱등성
- **FE** — `useAdminForceEnd`의 2단계 규칙(타임아웃 해제, 다른 행 건드리면 풀림, 409에서 행 제거).
  `useDealAction.spec.ts`가 같은 규칙을 검증하는 본보기다
- 컴포넌트는 렌더 스냅샷을 늘리지 않는다
