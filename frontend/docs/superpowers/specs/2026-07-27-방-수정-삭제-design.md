# 방 수정·삭제 — 설계

> S15P11A704-324 (방 수정 화면) · S15P11A704-325 (방 삭제 플로우)
> 2026-07-27

콘솔 대기 상태에 **버튼만 있고 눌리지 않는** 방 수정·방 삭제를 동작시킨다.
현재 `ConsoleView.vue:346,354`와 `BroadcastSlot.vue:70`이 `disabled` + `title="준비 중"`이다.

## 와이어프레임과 다르게 가는 부분

단일 기준은 `비드라이브 인터랙티브.html`의 `console` 섹션이다. 다만 **그대로 따르지 않는 지점이 셋**이고,
근거를 남긴다.

| 와이어프레임 | 이 설계 | 이유 |
| --- | --- | --- |
| `cEditRoom` → `go('create')` — 수정 전용 화면이 없다 | `/rooms/:id/edit` 신설 | 목업은 SPA라 라우트 개념이 없어 개설 화면으로 퉁친 것이다. `/rooms/new`로 보내면 **수정이 아니라 새 방 개설**이 된다 — 프리필도 대상 방 id도 없다 |
| `dropRoom` — 확인 없이 즉시 삭제 | 2단계 인라인 확인 | 되돌릴 수 없는 동작이다. 레포에 이미 같은 성격의 방송 종료가 2단계 확인(`endConfirming`, 5초 자동 해제)으로 있다 |
| `data-screen="edit"` 없음 | 신설하되 **폼 컴포넌트는 개설과 공유** | 와이어프레임의 "개설 화면을 재사용한다"는 의도는 컴포넌트 재사용으로 지킨다 |

`AGENTS.md`의 "와이어프레임이 기준"은 **화면 구성·문구**에 대한 규칙이고, 목업이 프로토타입이라
생략한 라우팅·확인 절차까지 그대로 베끼라는 뜻은 아니다.

## 명세 확인 결과

원문을 직접 읽었다 (`API 명세 테이블/경매방 수정`·`경매방 삭제`·`경매방 상세 조회`, 셋 다 **확정**).

**`PATCH /api/v1/auction-rooms/{auctionId}`** — 부분 수정. 안 보낸 필드는 서버가 유지한다.

- `product.{title,description,category,imageUrl}` · `auction.{reservePrice,durationMinutes,startType,scheduledAt}` 전부 선택
- `EMPTY_UPDATE_REQUEST`(400) — **수정 필드가 하나도 없으면 거절**한다
- `IMMEDIATE`로 바꾸면 서버가 `scheduledAt`을 제거한다
- 오류: `EMPTY_UPDATE_REQUEST` · `INVALID_AUCTION_REQUEST` · `UNAUTHORIZED` · `NOT_AUCTION_SELLER`(403) · `AUCTION_NOT_FOUND` · `AUCTION_UPDATE_NOT_ALLOWED`(409)
- ⚠️ **`AUCTION_HAS_PARTICIPATION`은 수정 명세에 없다.** 티켓 `-324` 본문이 틀렸다 — 삭제에만 있다

**`DELETE /api/v1/auction-rooms/{auctionId}`** — 204, 본문 없음.

- 오류: `UNAUTHORIZED` · `NOT_AUCTION_SELLER`(403) · `AUCTION_NOT_FOUND` · `AUCTION_ALREADY_STARTED`(409) · `AUCTION_HAS_PARTICIPATION`(409)

**`GET /api/v1/auction-rooms/{auctionId}`** — 프리필 소스인데 **부족한 게 있다.**

- 주는 것: `title` · `status` · `reservePrice` · `scheduledAt` · `durationMinutes` · `product.{productId,title,description,imageUrl}` · `seller` · `canEnter`
- **안 주는 것: `category`, `startType`, `conditionStatus`, 판매자 식별자**

## 화면 구성 — 단일 폼

개설은 1→2단계 마법사지만 **수정은 한 화면 단일 폼**이다.

수정은 PATCH — 부분 변경이 기본이라 "처음부터 끝까지 채우는" 마법사와 결이 다르다. 한 필드 고치려고
2단계를 지나게 할 이유가 없고, `EMPTY_UPDATE_REQUEST` 때문에 **변경분 유무를 화면이 계속 추적**해야 하는데
한 화면이어야 그걸 보여줄 수 있다.

`RoomCreateStep1`·`RoomCreateStep2`를 **그대로** 세로로 배치한다. 둘 다 `defineModel` 기반 순수 폼 섹션이라
(`title`·`description`·`categoryCode`·`conditionStatus`·`images` / `reservePrice`·`durationMinutes`·`startType`·`scheduledDate`·`scheduledTime`)
props는 `errors`(+`categories`)뿐이고 내부 상태가 없다. 수정할 필요 없이 재사용된다.

## 프리필

| 필드 | 소스 | 비고 |
| --- | --- | --- |
| `title` | `product.title` | |
| `description` | `product.description` | |
| `categoryCode` | **빈 값** | GET이 안 준다. "고르면 변경, 비우면 현재 카테고리 유지" 안내를 붙인다 |
| `images` | `product.imageUrl` 1장을 `sortOrder:1, isThumbnail:true`로 | 아래 「이미지」 참조. `imageUrl`이 빈 문자열이면 빈 배열 |
| `conditionStatus` | 빈 값 | API 페이로드에 없는 필드다 — **항상 페이로드에서 제외** |
| `reservePrice` | `reservePrice` | |
| `durationMinutes` | `durationMinutes` | |
| `startType` | `scheduledAt === null ? 'IMMEDIATE' : 'SCHEDULED'` | **추론이다.** 근거는 `ck_auction_room_schedule`(IMMEDIATE면 반드시 null) |
| `scheduledDate`·`scheduledTime` | `scheduledAt` 분해 | |

## 변경분 추적

프리필 직후 스냅샷을 보관하고 현재 값과 비교해 **바뀐 필드만** 페이로드에 넣는다.

- 하나도 안 바뀌면 저장 버튼 비활성 + "변경한 내용이 없어요" → `EMPTY_UPDATE_REQUEST`를 애초에 안 만난다
- `categoryCode`가 빈 값이면 `product.category` 생략
- `conditionStatus`는 언제나 생략
- `IMMEDIATE`로 바꾸면 `scheduledAt`을 안 보낸다 (서버가 제거)
- `product`·`auction` 객체도 **하위에 보낼 필드가 없으면 통째로 생략**한다

비교 규칙을 못 박는다 — 애매하면 구현이 갈린다:

| 필드 | "바뀌었다" 판정 |
| --- | --- |
| `title`·`description` | `trim()` 후 문자열 비교 |
| `category` | 빈 값이 아니고, 프리필이 빈 값이었으므로 **고르기만 하면 변경** |
| `imageUrl` | 대표 이미지의 `imageUrl`이 프리필 값과 다를 때 |
| `reservePrice`·`durationMinutes` | 숫자 비교. `null`이면 검증 실패로 저장 자체를 막는다 |
| `startType` | 추론값과 다를 때 |
| `scheduledAt` | `startType`이 `SCHEDULED`일 때만 비교. 날짜·시각을 합친 ISO 문자열 기준 |

## 이미지

`RoomCreateStep1`은 `URL.createObjectURL(file)`로 로컬 미리보기만 만든다 — **업로드 엔드포인트가 명세에 없어서**다.
그대로 두면 "사진을 바꿨다고 믿게 만드는" 화면이 된다.

업로드 엔드포인트는 **BE에 요청해 둔 상태라 곧 생길 예정**이다. 그래서 지금 막지 말고 **함수 하나로 격리**해
엔드포인트가 확정되면 그 함수 본문만 고치게 한다.

```
shared/api/uploads.ts
  uploadProductImage(file: File): Promise<string>   // → imageUrl
    목 모드 : mockDelay + URL.createObjectURL(file)
    실 모드 : POST multipart → { imageUrl }
```

- 실 모드 경로·필드명·응답 스키마는 **현재 추측이다.** 함수 상단에 그렇게 명시하고, 확정용 BE 티켓을 끊는다.
  추측을 코드에 조용히 묻어두지 않는다

**`RoomCreateStep1`의 이미지 UI는 손대지 않는다.** 그 블록은 다중 이미지(`ProductImageDraft[]`,
정렬·대표 지정)를 다루는데, 이걸 "사진 1장 교체" UI로 바꾸려면 Step1을 고쳐야 하고 그러면 개설 화면까지
영향을 받는다. 대신 **경계를 저장 시점에 둔다**:

- 프리필: `product.imageUrl` 1장을 `images` 배열에 `sortOrder: 1, isThumbnail: true`로 넣는다
- 사용자는 개설과 똑같은 UI로 추가·삭제·대표 지정을 한다
- 저장 시 **대표 이미지(`isThumbnail`) 1장만** `uploadProductImage()`에 태우고, 그 URL을 `product.imageUrl`로 보낸다.
  API가 단일 이미지라 나머지는 보낼 곳이 없다 — 이 사실을 이미지 블록 아래 한 줄로 안내한다
  ("대표 사진 1장만 저장돼요")
- 대표 이미지가 프리필 때와 같으면(= 새로 고르지 않았으면) 업로드도 전송도 하지 않는다 → 서버 값 유지
- 업로드 실패는 사진 영역 인라인 에러로만 표시하고 **나머지 필드 저장은 계속 가능**하게 둔다

개설 화면의 blob-URL 문제도 나중에 같은 함수로 흡수할 수 있다 (이번 범위 아님).

## 라우트·진입·복귀

`/rooms/:id/edit`, name `room-edit`, `features/room/RoomEditView.vue`.

- 진입: 콘솔 대기 상태의 "방 수정" → `router.push`
- 복귀: 저장 성공·취소 모두 **콘솔로**(`/rooms/:id/console`). 진입점이 콘솔 하나뿐이라 `useReturnTo` 같은
  복귀 경로 기억이 필요 없다
- 가드: 마운트 시 `getAuctionRoom`으로 `status !== 'WAITING'`이면 콘솔로 `replace` + 안내.
  서버도 `AUCTION_UPDATE_NOT_ALLOWED`로 막지만 화면이 먼저 거른다
- 헤더: 전체 화면이 아니라 일반 화면이다 — `meta.chrome`을 건드리지 않는다 (충전·출금과 다르다)

**판매자 판정은 콘솔과 같은 전제를 물려받는다.** 상세 응답에 판매자 식별자가 없어(`S15P11A704-326`)
FE가 "내가 이 방의 판매자인가"를 판정할 수 없다. 서버 `NOT_AUCTION_SELLER`(403)를 사후 처리한다.
콘솔이 이미 같은 상태로 동작하므로 이 화면만 새로 뚫는 구멍은 아니다.

## 삭제

진입점이 둘이다 — `ConsoleView.vue:354`("방 삭제")와 `BroadcastSlot.vue:70`("방 삭제하기").
와이어프레임도 `cDropRoom`·`cDropRoom2`가 같은 핸들러(`dropRoom`)를 쓴다.

`features/room/useRoomDelete.ts` composable로 묶어 두 곳이 같은 동작을 공유한다.
버튼을 하나로 합치지는 않는다 — 와이어프레임이 두 자리에 둔 배치다.

- 2단계 인라인 확인: 첫 클릭에 "한 번 더 누르면 삭제"로 바뀌고 **5초 뒤 자동 해제** (방송 종료와 동일)
- 성공 → **홈(`/`)**. 와이어프레임 `dropRoom`이 `go('main')`이다. 티켓 `-325`의 `/rooms`는 근거가 약하다
- 실패 문구 분리:
  - `AUCTION_ALREADY_STARTED` → "이미 시작된 방은 삭제할 수 없어요"
  - `AUCTION_HAS_PARTICIPATION` → "참여자가 있어 삭제할 수 없어요"
  - `NOT_AUCTION_SELLER` → "이 방의 판매자만 삭제할 수 있어요"
  - 그 외 → 공통 문구

## API 레이어 손볼 것

- **`updateAuctionRoom`에 목 분기가 없다.** 지금 목 모드에서 PATCH가 실 HTTP로 나가 깨진다.
  `createAuctionRoom`과 같은 형태로 목 응답을 추가한다 (`deleteAuctionRoom`은 이미 있다)
- `shared/api/uploads.ts` 신설

`stores/room.ts`는 **건드리지 않는다.** 그 스토어의 `createRoom`은 `shared/api`를 안 거치는 목 전용이고
페이로드 shape도 API 모듈과 다르다(`categoryCode`·`conditionStatus`·`images[]` vs `category`·`imageUrl`).
정리는 `S15P11A704-222`의 몫이다 — 이번에 끌어들이면 범위가 두 배가 된다.
수정 화면은 `shared/api/rooms.ts`를 직접 쓴다 (AGENTS.md 규칙 8).
