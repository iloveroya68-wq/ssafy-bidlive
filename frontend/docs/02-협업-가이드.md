  명세 「카카오 OAuth Callback」이 `{frontendBaseUrl}/oauth/callback`으로 못박았고

  `backend/docs/api/auction/`의 강제 종료(`DEAL-09`)다. **와이어프레임이 없으니 이 표가 유일한 정본이다** —
  「표와 와이어프레임을 대조한다」는 규칙이 여기서는 「표를 갱신한다」로만 성립한다.

베팅 포인트(BP)는 무료 재화라 충전·출금이 없다 — `charge`·`withdraw` 모두 거래 포인트 전용이다
(`docs/04` §3.5의 지갑 2행 구조와 일치).

### 라우트 설계 판단

**`/`는 세션에 따라 두 화면이 된다.** 와이어프레임의 `go('main')`은 `data-auth="out"`이면 `landing`으로 바꿔 보낸다.
경로를 나누지 않고 `/` 하나에서 세션 유무로 `LandingView`/`MainView`를 갈아 끼운다.
`/landing`을 따로 두면 로그인한 사용자가 그 링크를 받았을 때 갈 곳이 없고,
비로그인 사용자에게 `/`가 소개 페이지가 되는 게 와이어프레임의 동작이다.

**`main`과 `livelist`는 다른 화면이다.** 홈(`main`)은 캐러셀·마감 임박 중심의 큐레이션이고,
방 목록(`livelist`)은 검색·필터·무한 스크롤 중심의 탐색이다. 홈의 "전체 보기 →"가 목록으로 간다.
기존 표가 둘을 `/` 한 줄로 합쳐 놓았던 것이 오류다.

**방 개설 2단계는 라우트가 아니라 쿼리다.** `create`·`create2`는 별도 `data-screen`이지만
1단계 입력이 메모리에만 있어 2단계 URL을 새로고침하거나 공유해도 복원되지 않는다.
라우트는 `/rooms/new` 하나로 두고 단계는 `?step=1|2`로 표시한다 — 브라우저 뒤로가기가
"← 이전"과 같은 동작이 되고, 새로고침 시 스토어가 비어 있으면 1단계로 되돌린다.

> 구현 메모(S15P11A704-361): **단계 이동만 `push`다.** 다른 화면의 딥링크(`?tab=`·`?cur=`·목록 필터)는
> 이력을 더럽히지 않게 `replace`를 쓰는데, 마법사 단계는 이력 자체가 "← 이전" UI라 반대다.
> `?step=2`로 직접 들어와도 1단계 입력이 비어 있으면 URL까지 `?step=1`로 되돌린다.

**콘솔은 별도 라우트다.** 판매자와 구매자는 같은 방에서 완전히 다른 화면을 본다(`live` vs `console`).
`/rooms/:id/live` 안에서 역할 분기하면 한 컴포넌트가 두 화면을 떠안는다.
와이어프레임 헤더 내비게이션에도 "진행 콘솔"이 독립 항목으로 있다.

**유찰은 결과와 별도 라우트다.** `nosale`은 낙찰자·미낙찰자가 존재하지 않아 역할 분기 자체가 없고,
정산 카드 구성도 `result`와 다르다. 방 종료 후 진입 시 서버 결과에 따라
`/rooms/:id/result` ↔ `/rooms/:id/nosale`로 리다이렉트한다.
`result_status` ↔ `data-why` 매핑은 와이어프레임 `NOSALE` 데이터로 확정했다 (2026-07-22).
`NO_SALE` → `nobid`·`left` (badge "유찰"), `CANCELLED` → `forced` (badge "강제 종료").
`forced`만 **재등록 버튼을 숨긴다** — 제재 검토 중인 상품을 그 자리에서 다시 올리게 두면 안내와 모순되기 때문이다.
`nobid`와 `left`를 가르는 건 `termination_reason`인데 값 목록이 아직 없다 (`docs/04` §6.1).

**충전·출금은 라우트이고 직전 화면으로 복귀한다.** 와이어프레임에서 이 둘은 헤더 지갑 칩·마이페이지 지갑 탭·
라이브 시청 중 어디서든 열리고, 완료·취소하면 **들어오기 직전 화면으로 돌아간다**
(스크립트의 `chargeReturnTo`). 라우트로 두되 진입 직전 경로를 `route.query.from` 또는 스토어에 기억해 복귀시킨다.

### 화면 내 상태 (라우트가 아님)

| 화면 | 상태 | 값 | 분기 소스 |
|---|---|---|---|
| `result` | `data-role` | `win` / `lose` / `bet` / `none` | **스토어(서버 판정)** — 쿼리 금지 |
| `console` | `data-state` | `wait` / `live` | **스토어(방 상태)** |
| `nosale` | `data-why` | `nobid` / `left` / `forced` | **스토어(서버 결과)** |
| `ledger` | `data-cur` | `trade` / `bet` | 쿼리 `?cur=trade\|bet` |
| `mypage` | `vtabs` | `wallet` / `todo` / `deals` / `board` | 쿼리 `?tab=` |
| `mypage` › 경매 목록 | `stabs` | `won` / `host` / `join` | 컴포넌트 로컬 상태 |
| `livelist` | `stabs` + 칩 + 검색 | `live`/`wait`/`done`, 카테고리, 검색어 | 쿼리 `?state=`·`?cat=`(**카테고리 코드**)·`?q=` — 셋 다 서버 조건으로 나간다 |
| `live` | 독 모드 | 입찰 / 예측 (배타, `03-역할-경계-합의.md` §4-1) | 컴포넌트 로컬 + `live` 스토어 |

판단 기준은 **그 링크를 받은 사람이 같은 화면을 봐야 하는가**다.
`result`의 역할, `nosale`의 사유, `console`의 상태는 **서버가 판정하는 사실**이라 URL로 지정할 수 있으면 안 된다
(관전자가 `?role=win`으로 낙찰자 화면을 여는 일이 없어야 한다).
반대로 원장 통화·마이페이지 탭·목록 필터는 "여기 이 탭을 보라"고 링크를 보내는 게 자연스러워 쿼리로 둔다.
경매 목록 안의 하위 탭(`won`/`host`/`join`)은 이미 `?tab=deals`로 들어온 뒤의 2차 분류라 URL까지 끌고 가지 않는다.

와이어프레임 검증 결과 `console`의 `data-state`는 **`wait`·`live` 2종뿐이고 `done`은 없다.**
방송을 종료하면 콘솔에 머무르지 않고 낙찰 공개 연출을 거쳐 `result`/`nosale`로 이동한다.
**판매자 전용 종료 후 화면은 아직 미확정이다.** 와이어프레임 조사 결과만 적어두면 —
`result`의 역할은 `win`·`lose`·`bet`·`none` 4종뿐이라 **판매자 역할이 없고**,
판매자의 정산·발송은 마이페이지 "지금 할 일"의 에스크로 전이
(`배송지 입력 → 발송했어요 → 받았어요 → 정산 완료`)가 담당한다.
즉 와이어프레임만 따르면 판매자는 `result`의 `none`(관전) 뷰를 보게 된다.

다만 그 경우 판매자에게는 **판매 대금 정산 카드가 어느 화면에도 없다** — 낙찰가는 보이지만
"내가 얼마를 받는지"가 결과 화면에 없고 마이페이지로 흩어진다.
판매자 전용 뷰(`data-role`에 `sell` 추가)를 만들지, 와이어프레임대로 관전 뷰로 둘지는 **결정 대기**다.

### `console` 담당 — FE1 확정 (2026-07-22)

콘솔의 구성 요소는 넷이다. ① 입찰 건수·참여자·남은 시간 지표 카드(대기 상태에서는 대기 인원·알림 신청·시작까지),
② 연장(최대 3회)·지금 시작·방송 종료·방 수정/삭제 제어, ③ 미답변 질문 큐, ④ 송출 미리보기 + 카메라·마이크 토글.

①②③은 FE1이 이미 맡은 방 관리·입찰 패널·결과 리포트와 같은 종류의 제어·통계 UI다.
FE2 고유 기술이 필요한 부분은 ④의 **로컬 송출 프리뷰**뿐이다.
그래서 **화면 전체는 FE1이 만들고, 송출 프리뷰 블록만 FE2가 `features/live/media/`에 컴포넌트로 제공해
FE1이 꽂는 형태**로 확정했다. LiveLayout `#video` 슬롯과 같은 패턴이라 새 계약이 필요 없다.
FE2의 3주차가 WebRTC 본작업으로 이미 가득 차 있다는 점(`03-역할-경계-합의.md` §8)도 근거다.

**우측 열은 `400px`이다** (S15P11A704-445). 프리뷰가 `aspect-video w-full`이라
**열 폭이 곧 프리뷰 크기**인데, 와이어프레임의 `320px`은 프리뷰 자리가 `height:150px`
회색 자리표시자일 때 맞춘 폭이었다 — 실제 카메라가 붙으면 16:9라서 약 288×162px가 되고,
판매자가 송출 전 자기 구도·조명을 점검하기엔 작다. 400px에서 약 368×207px.

와이어프레임을 코드에 맞춰 두지 않으면 다음에 대조하는 사람이 "표가 틀린 건가"에서 멈추므로
**프로토타입도 같이 고쳤다** — 열 `400px` + 자리표시자 `aspect-ratio:16/9`
(디자인 레포 PR #8). 즉 이 값은 와이어프레임과 어긋나지 않는다.

## 화면 이동 흐름

와이어프레임의 `data-go` 속성과 스크립트의 `go()` 호출을 전수 조사한 결과다.

**비로그인 진입 → 가입 → 온보딩**

| 출발 | 동선 | 도착 |
|---|---|---|
| `/` | 비로그인이면 홈 대신 랜딩 | `landing` |
| `landing` | "3초 만에 시작하기 →" · 하단 카카오 CTA | `signup` |
| `landing` | "라이브 구경하기" | `livelist` |
| `landing` | "이미 계정이 있다면 로그인" | `login` |
| `login` ↔ `signup` | 서로 상대 화면 링크 — 신규·기존을 막지 않는다 | — |
| `login`/`signup` | 카카오 인증 — **첫 로그인**(닉네임 없음 또는 필수 약관 미동의) | `onboard` |
| `login`/`signup` | 카카오 인증 — **기존 회원** | `main` |
| `onboard` | 닉네임 + 필수 약관 동의 후 "BidLive 시작하기" | `main` |

비로그인 상태에서는 헤더의 방 개설·진행 콘솔·마이페이지 링크가 숨겨진다(와이어프레임 CSS `body[data-auth="out"]`).
라우터 가드로 옮길 때도 같은 범위를 막는다.

**구매자 동선**

| 출발 | 동선 | 도착 |
|---|---|---|
| `main` | 캐러셀 카드 · 마감 임박 카드 | `live` |
| `main` | "전체 보기 →" · 헤더 "라이브" | `livelist` |
| `livelist` | 방 카드 — 방 상태 `live` | `live` |
| `livelist` | 방 카드 — 방 상태 `wait` | `wait` |
| `livelist` | 방 카드 — 방 상태 `done` | `result` (관전 역할) |
| `wait` | 판매자가 방송 시작 → 자동 전환 | `live` |
| `wait`/`live` | 뒤로가기 버튼 · "목록으로" | `livelist` |
| `live` | 하단 "다른 라이브" 카드 | `live` (다른 방) |
| `live` | 마감 → 집계 연출 → "낙찰 결과 자세히 →" | `result` |
| `live` | 마감 → 집계 연출 → "유찰 안내 자세히 →" | `nosale` |
| `live`/`wait` | 신고 누적 강제 종료 오버레이 → "정산 내역 보기" | `nosale` (`why=forced`) |
| `result` | "다른 방송 보러 가기 →" | `livelist` |
| `result` (낙찰자) | "배송 정보 입력하기" | 배송지 모달 (화면 이동 없음) |

강제 종료는 화면을 갈아끼우지 않고 보던 방송 위를 덮는 오버레이다 — `live`·`wait` 양쪽에 있고,
대기방에서는 잠겨 있던 입찰이 없으므로 "해제할 홀드가 없다"로 문구가 갈린다.

**구현 현황 (2026-07-23)** — 위 표는 와이어프레임 기준이고, 코드가 아직 못 따라간 곳이 둘이다.

- `result`(낙찰자) "배송 정보 입력하기"는 **표가 맞고 코드가 다르다.** 배송 플로우가 Phase 3 범위 밖이라
  지금은 모달 대신 `/me`로 보낸다. 모달 신설은 **S15P11A704-268**.
- 강제 종료 오버레이는 `live`에만 있다. 대기방 쪽은 **S15P11A704-269**의 2번이고,
  그 전제인 상시 신고 버튼은 **S15P11A704-74**다.

**판매자 동선**

| 출발 | 동선 | 도착 |
|---|---|---|
| `main` · 헤더 | "＋ 경매 방 개설" | `create` |
| `create` | "다음 · 경매 조건 →" | `create2` |
| `create` | "취소" | `main` |
| `create2` | "← 이전" | `create` |
| `create2` | 시작 방식 **지금 바로 시작** → "방송 개설하기" | `console` (`state=wait`) |
| `create2` | 시작 방식 **예정 시각 지정** → 개설 | `console` (`state=wait`) |
| `console` (`wait`) | "지금 시작하기" | `console` (`state=live`) |
| `console` (`wait`) | "방 수정" | `create` |
| `console` (`wait`) | "방 삭제" / "방 삭제하기" | `main` |
| `console` (`live`) | "＋ 방송 5분 연장" (잔여 3회) | 제자리 갱신 |
| `console` (`live`) | "방송 종료" → 낙찰 공개 연출 | `result` / `nosale` |
| `nosale` | "이 상품 다시 등록하기" (판매자 전용, 강제 종료 시 숨김) | `create` |

와이어프레임의 `create2` "방송 시작하기"는 시연 편의상 구매자 `live`로 가지만,
개설자는 판매자이므로 실제 구현에서는 `console`로 보낸다(위 표는 실제 동선 기준).

**「지금 바로 시작」을 골라도 도착지는 `console` (`state=wait`)이다** (S15P11A704-222).
ROOM-01 검증 규칙이 *"어떤 시작 방식이든 생성 직후 상태는 `WAITING`이고, 판매자가 방송 시작 API를
호출하기 전에는 입찰·예측을 받을 수 없다"*고 못 박았다 — 개설(ROOM-01)과 방송 시작(ROOM-05)은
**별개 호출**이다. 그러니 시작 방식은 도착지를 가르지 않고, 「지금 시작하기」를 한 번 더 눌러야 라이브가 된다.
이 표는 2026-07-29까지 `IMMEDIATE`면 곧장 `state=live`라고 적고 있었는데, 그때는 스토어가
개설 응답에 없는 `LIVE`를 지어내고 있어서 화면상 맞아 보였을 뿐이다.

**지갑·마이페이지 동선**

| 출발 | 동선 | 도착 |
|---|---|---|
| 헤더 아바타 | 마이페이지 | `mypage` (기본 탭 `wallet`) |
| 헤더 지갑 칩 | 충전 | `charge` |
| `mypage` › 지갑 탭 | 거래 포인트 카드 "거래 내역 보기 →" | `ledger` (`cur=trade`) |
| `mypage` › 지갑 탭 | 베팅 포인트 카드 "베팅 내역 보기 →" | `ledger` (`cur=bet`) |
| `mypage` › 지갑 탭 | 거래 카드의 "충전" / "출금" 버튼 | `charge` / `withdraw` |
| `ledger` | "← 마이페이지" | `mypage` |
| `charge` / `withdraw` | 완료 또는 취소 | **진입 직전 화면** (없으면 `mypage`) |
| `mypage` | "로그아웃" | `login` |
| `main` / `livelist` 티커 | 예측 수익률 스트립 클릭 | `mypage` (`tab=board`) |

마이페이지 기본 탭은 `wallet`이다 — 지갑이 비면 아무것도 할 수 없는 구조라 진입 즉시 잔액을 보여준다.
"지금 할 일" 탭에는 **내가 움직여야 하는 건만** 올라가고 개수 배지를 상시 노출한다(DEAL-07).

## 현재 구현과의 차이

아래 표는 **슬라이스 0 이전**의 `src/app/router.ts`(10개 라우트)를 와이어프레임과 대조한 기록이다.
경로 재편이 끝난 지금은 **19개 엔트리**(명명 라우트 18 + `/wallet` → `/wallet/ledger` 리다이렉트 1)다.
(2026-07-31 실측으로 갱신 — `/admin` 신설 전에 이미 「16 + 1」이 아니라 「17 + 1」이었다.)
표를 지우지 않고 완료된 행에 결과를 덧붙여 둔다 — 왜 이렇게 옮겼는지가 남아 있어야 해서다.

> **진행 상황 (2026-07-24, S15P11A704-305 「슬라이스 0」).** 아래 표의 **경로 재편은 완료**됐다 —
> `/` 세션 분기(`landing`/`main`), 목록 `/rooms` 이동, `/signup`·`/rooms/:id/console`·`/wallet/charge`·
> `/wallet/withdraw` 신설, `/wallet` → `/wallet/ledger` 리다이렉트. 라우트 이름 `room-list`·`wallet`은
> 기존 호출부 보호를 위해 유지했다. 전역 헤더 `shared/ui/AppHeader.vue`도 이때 신설됐다(그전엔 없었다).
>
> **갱신 (2026-07-26).** 화면 틀 스캐폴딩 **슬라이스 0~6이 모두 끝났다** — `landing`(1) · `main`(2) ·
> `signup`(3) · `console`(4) · `charge`(5) · `withdraw`(6). stub으로 남은 라우트 화면은 없다.
>
> 충전·출금은 전체 화면이고 헤더를 띄우지 않는다(`meta.chrome = false`). 어디서 눌렀는지를
> `redirect` 쿼리로 넘겨 완료·취소 시 그 자리로 돌아온다 — 복귀 처리는 `features/wallet/useReturnTo.ts`가
> 두 화면에 공통이다. 모달(`ChargeModal`·`WithdrawModal`)은 이전이 끝나 삭제됐다.
>
> `MyPageView`도 1차(프로필 헤더·탭 틀·지갑 탭)가 들어갔다(334). 원장 진입이 지갑 카드의
> "거래/베팅 내역 보기 →"로 살아나면서 **헤더 지갑 칩은 와이어프레임 원본대로 칩 전체가 충전**이다.
>
> 회원가입 CTA는 이전이 끝나 `/signup`을 직접 가리킨다(헤더 1 · 랜딩 2곳).
> 구 경로 `/login?mode=signup`은 라우터 가드가 `/signup`으로 옮긴다.
>
> **갱신 (2026-07-27).** **마이페이지 4탭이 전부 찼다** — 경매 목록(낙찰/개최/참여)과 `?tab=` 딥링크가
> 335, 지금 할 일·리더보드가 336. 이로써 와이어프레임 17개 화면에 **stub도 미구현도 없다.**
>
> 다만 「지금 할 일」의 항목은 **아직 링크가 아니다.** 서버가 주는 `actionPath`(`/deals/300/address` 등)에
> 대응하는 FE 라우트가 없어 라벨·설명만 보여준다 — 거래 화면은 `S15P11A704-337`이 받는다.
> 리더보드는 마이페이지 탭과 **홈 티커 둘 다 실 API**(`getDailyLeaderboard`)를 쓴다(`-76`).
> 목 분기는 2026-08-01에 없앴다(`547`) — **인증이 필요한 엔드포인트라 비로그인 홈에서는 401**이고,
> 티커는 그때 조용히 접힌다(오류 배너를 띄우지 않는다).
> 순위 표기·수익률 서식은 `shared/lib/leaderboard.ts`가 단일 소스다 — 두 화면이 각자 들고 있었고
> 기준(0-based 인덱스 ↔ 1-based `rank`)까지 달랐다.
>
> ⚠️ **「시연도 목 모드로 돈다」는 전제는 2026-07-30에 끝났다(S15P11A704-504).** 백엔드가 구현한
> 엔드포인트의 목 분기를 걷어내면서 홈·방 목록·상세·**대기방 입장(join)**이 목 스위치와 무관하게
> 실 호출이 됐다. 그래서 **프론트를 띄우려면 로컬 백엔드가 필요하다** — 없으면 첫 화면부터 오류이고,
> 아래 트리거들은 화면에 도달하지 못해 무용지물이 된다(대기방 목 드라이버는 남아 있지만
> join이 먼저 실패한다). 목이 남은 범위는 `shared/api/mock.ts` 머리말이 단일 소스다.
>
> **목 전용 트리거 쿼리는 딥링크와 별개다** — 화면 상태를 공유하려는 값이 아니라 목 모드에서만 켜지는
> 검증·시연 스위치다. 현재 셋이다: 마감 연출 `?reveal=sold|nosale|canceled`(`live`),
> 채팅 통지 시연 스트립 `?chatdemo=1`(`ChatPanel` — 검열 경고·전송 실패·재연결·중복 메시지,
> S15P11A704-453), 스테이지 오디오 컨트롤 `?audiodemo`(`LiveStage` — 스피커·음량 슬라이더, 470·475).
> 실 모드에서는 쿼리를 붙여도 나오지 않는다.
>
> **기본값은 둘이 갈린다**(`useMockDemoFlag(key, defaultOn)`).
> `?reveal`·`?chatdemo`는 기본 끔이고, **`?audiodemo`만 기본 켬이라 끄는 표기(`?audiodemo=0`)를 쓴다.**
> 앞의 둘은 시연 화면을 더럽히지 않는 쪽이 중요하고(당시 전제는 「시연도 목 모드로 돈다」였다 — 위 경고 참조), 오디오 컨트롤은
> 목 모드에 원래 안 뜨는 것이라(미디어 서버가 없어 `hasStream`이 false) 켜지 않으면 배치·펼침·키보드를
> 확인할 방법 자체가 없었다 — 확인 비용이 「소리 안 나는 슬라이더가 보인다」는 위험보다 컸다(475).
> 시연에서 감춰야 하면 링크에 `?audiodemo=0`을 붙인다.
>
> 쿼리 딥링크는 **`?tab=`·`?cur=`·`?step=`·`?state=`·`?cat=` 다섯이 모두 동작한다**
> (`-335`·`-340`·`-361`). 규약은 하나다 — **쿼리가 정본이고 화면 상태는 그 사본**이며,
> 알아볼 수 없는 값은 URL까지 정규화한다. 이력 정책만 갈리는데, 필터·탭은 `replace`이고
> 개설 단계(`?step=`)만 `push`다(뒤로가기가 "← 이전"이어야 해서).
>
> 단 `?cat=`은 **판정을 미룬다** — 값이 카테고리 코드(`?cat=ELECTRONICS`)이고 그 목록이
> 서버에서 오기 때문에, 목록이 도착하기 전에 "모르는 값"으로 처리하면 정상 링크를 열자마자
> 쿼리를 지워 버린다(S15P11A704-397).
>

**지갑 건 (이번 재작성의 발단).** 낡은 표의 `/wallet` = "이중 지갑 + 원장" 한 줄을 근거로
잔액 카드와 원장을 한 페이지에 담은 `WalletView.vue`를 만들었으나, 와이어프레임에 그런 화면은 없다.
실제 구조는 **마이페이지 `지갑` 탭 = 거래/베팅 카드 2장**(잔액 + 충전·출금 버튼)이고,
각 카드 하단의 "거래 내역 보기 →"·"베팅 내역 보기 →"를 누르면 **별도 `ledger` 화면**으로 넘어간다.
`ledger`는 자체 통화 탭(`trade`/`bet`)·잔액 헤더·무한 스크롤을 가지고 "← 마이페이지"로 복귀한다.
따라서 `/wallet` 단독 라우트는 폐지하고, 잔액 카드는 `/me?tab=wallet`으로, 원장은 `/wallet/ledger`로 옮긴다.
`WalletView.vue`가 `docs/04` §3.5에서 끌어낸 판단(available/held 분리 표시, 원장 두 테이블 분리,
홀드 행 라벨링, append-only)은 그대로 유효하므로 **로직은 보존하고 배치만 두 화면으로 나눈다.**

`/wallet/ledger`는 **"현재 잔액" 한 줄(available)만** 둔다 — 와이어프레임 `ledger` 대조 결과로 확정했다.
available/held 분리 표시는 마이페이지 지갑 카드 쪽 몫이다.
