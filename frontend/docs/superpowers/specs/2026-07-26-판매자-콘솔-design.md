# 판매자 콘솔 (화면 틀 슬라이스 4) — 설계

- Jira: `S15P11A704-70`
- 상위 설계: `2026-07-24-화면-틀-스캐폴딩-design.md`의 작업 분할 표 슬라이스 4
- 대조 원본: 와이어프레임 `data-screen="console"` (`data-state`는 `wait`/`live` 2종, `done` 없음)
- 라우트·stub은 슬라이스 0(`S15P11A704-305`)에서 이미 연결됨 — 이 슬라이스는 **내용을 채우는 작업**이다.

## 1. 목표와 범위

판매자가 자기 방을 진행하는 화면. 대기(시작 전)와 라이브(진행 중) 두 상태를 한 라우트가 겸한다.

**하는 것**

- 대기: 대기 인원 · 알림 신청 · 시작까지 카운트다운, 지금 시작하기, 방 수정·삭제 진입점
- 라이브: 입찰 건수 · 참여자 · 남은 시간 3박스, 5분 연장(잔여 N/3), 방송 종료
- 미답변 질문 큐 (CHAT-06)
- 송출 프리뷰 **슬롯** — 자리와 컨트롤 껍데기만. `features/live/media/`는 FE2 소유라 건드리지 않는다
- 판매자가 아닌 사람이 URL로 들어왔을 때의 처리

**안 하는 것**

- 방 수정 화면(`/rooms/:id/edit`)과 삭제 플로우 — 버튼은 두되 "준비 중" 안내, 후속 이슈로 끊는다
- 실제 송출(OpenVidu 연결·스트림 바인딩) — FE2
- 종료 상태(`done`) 화면 — 와이어프레임에 없다. 종료는 결과(`/rooms/:id/result`)·유찰(`/nosale`)이 받는다

## 2. 파일 구성

새 디렉터리 `src/features/console/` (현재 `ConsoleView.vue` stub 하나만 있다).

| 파일 | 역할 | 의존 |
| --- | --- | --- |
| `ConsoleView.vue` | 프레임. 방 상세 조회, 진입 가드, 좌(1fr)/우(320px) 2열, 상태 분기, 시연 토글 | `rooms.ts`, `stores/live`, 아래 3개 |
| `ConsoleMetrics.vue` | 지표 3박스. 대기 세트와 라이브 세트를 상태에 따라 그린다 | props만 (스토어 접근 없음) |
| `QuestionQueue.vue` | 미답변 질문 큐. 목록·답변 완료 처리 | props + emit |
| `BroadcastSlot.vue` | 송출 미리보기 자리, 카메라·마이크 컨트롤, 대기 점검 리스트, 종료/삭제 버튼 | props + emit |

세 자식은 **스토어를 직접 읽지 않는다**. 데이터는 `ConsoleView`가 모아 props로 내린다 — 자식만 보고 무엇을 그리는지 알 수 있어야 하고, 나중에 FE2가 `BroadcastSlot` 안을 채울 때 스토어 결합이 없어야 갈아끼우기 쉽다.

공통 컴포넌트(`shared/ui/`) 추출은 하지 않는다. 지표 박스·큐 항목 모두 이 화면에서 처음 등장한다 (AGENTS.md 컨벤션: 두 번째 등장 때 추출).

## 3. 상태 모델

표시 상태는 `wait` / `live` 둘뿐이고, 판정 소스는 `live` 스토어의 `auctionStatus`(`WAITING`/`LIVE`/그 외)다.

- `LIVE` → `live` 세트
- 그 외 → `wait` 세트
- 상태는 **서버 판정이라 URL로 지정하지 않는다.** 와이어프레임의 `demorow` 토글은 **목 모드에서만** 노출하고,
  콘솔 **로컬 ref**로 표시 상태를 덮는다. `stores/live.ts`는 FE2 소유라 읽기만 하고 쓰지 않는다.

## 4. 데이터 흐름

### 4.1 방 정보 — `getAuctionRoom(id)` (`shared/api/rooms.ts`)

`AuctionRoomDetail`에서 `title`·`status`·`scheduledAt`·`viewerCount`를 쓴다.

### 4.2 라이브 지표 — `live` 스토어 (읽기 전용)

| 표시 | 소스 | 값이 없을 때 |
| --- | --- | --- |
| 입찰 건수 | `live.bidCount` | `—` (null = 스냅샷 미수신. "0건"으로 단정하지 않는다) |
| 참여자 | `live.participantCount` | `—` |
| 남은 시간 | `useCountdown(live.endsAt, { serverOffset: live.serverOffset })` | `--:--` (규칙 5 — `Date.now()` 단독 계산 금지) |
| 잔여 연장 | `live.remainingExtensions` / 최대 3 | `—` |

콘솔 진입 시 `live.connect(roomId)`, 이탈 시 `disconnect()`. 목 모드에서는 목 소켓 피드가 지표를 흘려보낸다.

### 4.3 대기 지표

| 표시 | 소스 |
| --- | --- |
| 대기 인원 | `live.viewerCount` (LIVE-03 활성 세션 수) |
| 알림 신청 | **없다.** 자리는 두고 값은 `—` + 안내 |
| 시작까지 | `scheduledAt` 기준 카운트다운. `serverOffset`이 없으면 `--:--` |

**"알림 신청"에 목 숫자를 넣지 않는다.** 대응 API가 명세 전체에 없다. 그럴싸한 값을 채우면 틀려도 화면이
멀쩡해 보여서 발견되지 않는다(`docs/04` §6의 `predictionParticipantCount` 사례). BE 확인 이슈로 끊는다.

### 4.4 질문 큐 — 전용 API (`shared/api/questions.ts` 신설)

**정정(구현 중 발견):** 처음엔 `live.chat`에서 `isQuestion`을 걸러 쓰려 했으나, 명세 원문을 열어 보니
CHAT-06 전용 REST가 실재한다. 채팅 메시지와 **다른 엔티티**이고 식별자도 `questionId`(ULID 문자열)다.

| API | 용도 |
| --- | --- |
| `GET /auctions/{id}/questions` | PENDING 질문만 커서 조회. **호스트 전용** |
| `DELETE /auctions/{id}/questions/{questionId}` | 답변 완료 → RESOLVED 전이. 이미 처리된 건도 204(멱등) |

따라서 답변 완료는 로컬 제거가 아니라 서버 호출이고, 실패해도 `QUESTION_NOT_FOUND`면 화면에서 지운다.
실시간 추가·제거(WS 「질문 큐 수신」)는 소켓 핸들러가 FE2 소유라 이번 범위 밖 — 후속으로 끊는다.

### 4.5 액션

| 버튼 | 호출 | 비활성 조건 |
| --- | --- | --- |
| 지금 시작하기 | `startAuctionRoom(id)` (`rooms.ts`) | 요청 진행 중 |
| ＋ 방송 5분 연장 | `extendAuction(id)` (`bids.ts`, BID-03) | 잔여 0회, 남은 시간 1분 미만, 요청 진행 중 |
| 방송 종료 | `endLiveStream(id)` (`features/live/media/api.ts`, LIVE-02) | 요청 진행 중 |
| 방 수정 / 방 삭제 | 없음 — "준비 중" 안내 | 항상 |

`endLiveStream`은 FE2 소유 파일의 함수지만 **import만 한다**(AGENTS.md 규칙 4: import 자유, 내부 수정만 합의 대상).
실패는 `ApiError.message`를 화면 상단 배너로 띄운다. 연장 실패 코드(`EXTENSION_LIMIT_EXCEEDED`·`EXTENSION_TOO_LATE`)는
이미 `errors.ts`에 있다.

## 5. 진입 가드 — 판정 근거가 없다

**`AuctionRoomDetail`에 판매자 식별자가 없다.** `seller`는 마스킹된 `nickname`(`판**`)과 `rating`뿐이고,
`sellerId`는 방 **생성** 응답(`CreateAuctionRoomResponse`)에만 있다. 즉 방 상세만으로는
"내가 이 방의 판매자인가"를 프론트가 판정할 수 없다.

이번 슬라이스의 처리:

1. **목 모드**: 통과시킨다(시연 가능해야 한다). 이유를 주석과 MR에 남긴다.
2. **실 모드**: 진입 시 호출하는 **질문 큐 조회가 호스트 전용**이라, 그 403 `NOT_AUCTION_HOST`를
   진입 판정으로 쓴다(§4.4에서 API를 찾은 뒤 확정). 판매자 전용 액션의 `NOT_AUCTION_SELLER`도 같은
   상태로 모은다. 다른 API의 권한 성질을 빌린 **우회 판정**이라는 점은 그대로다.
3. **BE 확인 이슈**를 새로 만든다 — 방 상세 응답에 `sellerId`(또는 `isSeller`/`canManage`) 추가 요청.
   에픽 `S15P11A704-321` 아래에 단다.

가드가 확정되면 1·2를 걷어내고 조건 한 줄로 바꾼다.

## 6. 레이아웃

와이어프레임 그대로: `max-width:1180px`, `grid-template-columns: 1fr 320px`, `gap:16px`.
좁은 폭에서는 우측 송출 카드가 아래로 떨어지도록 `lg:` 브레이크포인트에서만 2열을 적용한다.

색은 토큰만 쓴다: 라이브 배지·긴급 타이머는 레드(`terra`/`red`), 대기 배지·질문 큐 카운트는 `slate`,
송출 프리뷰 배경은 `stage`, 위험 액션(종료·삭제)은 레드 계열. 새 색은 추가하지 않는다.

## 7. 검증

1. `npm run format:check` · `npm run lint` · `npm run build`
2. 와이어프레임 `data-screen="console"`과 1:1 대조 (대기/라이브 두 상태 모두)
3. 브라우저:
   - 콘솔 대기 → 지금 시작 → 라이브 전환, 연장 버튼 잔여 표시·비활성 조건
   - 질문 큐 표시와 답변 완료 제거
   - **회귀**: `/rooms/:id/live`·`/rooms/:id/waiting` — 같은 `live` 스토어를 `connect`/`disconnect`하므로
     콘솔을 거친 뒤 두 화면이 정상인지 반드시 확인한다. 이 슬라이스에서 제일 위험한 지점이다.
4. 하드코딩 색·폰트 없음 (신규 파일은 `git add -A` 후 `--cached`로 확인)
5. FE2 소유 파일 무변경: `features/live/media|socket/`, `features/chat/`, `stores/live.ts`
